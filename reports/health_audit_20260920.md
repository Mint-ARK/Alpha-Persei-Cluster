# 第1轮｜请求分发、商店扣费与响应时序

扫描日期：2026-09-20。问题编号：A01、A02、A03、A04。

## A01｜商店按客户端上报金额扣费，可能绕过配置价格

### 出现什么现象

商品按客户端报出的金额成交，少报金额或提供零数量条目时，仍可能发货并记录购买次数。

### 初步定位

buy_goods 在 cost_items 非空时直接采用请求中的物品编号和数量，没有对照服务端商品价格，也没有按购买数量核对总额；零数量条目跳过扣费后仍继续发货。

### 相关文件与入口

| 文件 | 定位入口 |
| --- | --- |
| `shop_service.py` | buy_goods |
| `operations.py` | ShopBuyOp |
| `shopaction.lua` | 20012 购买请求 |

## A02｜事件监听器内部报错后被再次调用，同一事件可能执行两遍

### 出现什么现象

一次事件触发后，监听器已经执行了一部分操作，报错后却又被再次调用。

### 初步定位

事件总线把监听器函数内部的 TypeError 当成参数不兼容，改用其他参数形式重新调用。允许多种参数形式的监听器因此可能重复执行已有操作。

### 相关文件与入口

| 文件 | 定位入口 |
| --- | --- |
| `event_bus.py` | EventBus.emit |

## A03｜业务已保存但回包失败，客户端重试可能再次扣费

### 出现什么现象

资产或进度已经保存，客户端却收到操作失败；再次操作可能重复消费。

### 初步定位

Core 的事务只包裹 apply，提交之后才调用 respond 组装回复。回复组装报错时，前面的业务变化已提交，错误回复无法将其撤销。

### 相关文件与入口

| 文件 | 定位入口 |
| --- | --- |
| `core.py` | Core._run_operation 的 apply、事务提交与 respond 顺序 |

## A04｜新请求清空待发通知，上一次操作的刷新包丢失

### 出现什么现象

请求开始时生成的资产变化或待发通知，在业务处理前被清掉。

### 初步定位

请求入口先重置上下文并触发周期处理，进入 _run_operation 后又重置一次。第二次重置会清除期间写入的 touched_items、removed_equips 和 pending_frames。

### 相关文件与入口

| 文件 | 定位入口 |
| --- | --- |
| `core.py` | dispatch、_run_operation |
| `middleware.py` | HandlerCtx.reset_operation_state |
| `server_net.py` | pulse_heartbeat 调用位置 |
