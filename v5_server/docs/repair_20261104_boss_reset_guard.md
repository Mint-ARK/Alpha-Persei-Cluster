# A83 梦境领奖后的重置保护及失败恢复

2026-11-04。核对第58轮、当前45006/45106/45204注册Operation、AccountDB、原生ResetBoss/ResetHardMode回调。没有改客户端Lua。

## 修改

- 普通和进阶单首领重置先严格读取当前模式/周期，要求目标为当前轮换中的合法首领。未知目标或模式错误返回2；查询失败不能当成未领。
- AccountDB的普通、进阶单首领及整轮重置方法自身增加保存点与严格领史检查。普通单首领检查本期普通领奖，进阶单首领检查本期进阶领奖；整轮/重选模式入口由普通和进阶界面共用，检查本期所有已领记录。已领返回2013，不清成绩、角色锁定、模式或领史。
- 两张进阶成绩表与模式修改同事务；直接调用或嵌套调用方法也不会留下半次重置。先执行现有惰性刷新，上一期领史不会阻止新一期重置。
- 保留重置本身既有范围：单首领只清对应进度和锁定；预设阵容与词缀保留，不将预设误当锁定。整轮方法仍清进阶两表并将模式设0，不借此新增普通进度清除策略。
- 三个Operation使用BossResetOperation并预提交准备必要ACK。成功只发ACK，Lua原有本地重置足够，不再发冗余45001/45101。

## 为什么失败后必须恢复

BattleBossChallengeAction的45007/45107回调不检查result就ResetBoss；45205回调先AdvanceData.Init与BossData.Reset，再将结果交给页面。页面随后才检查result。所以只拒绝服务端请求仍会把客户端数据临时清空；把全量状态放在ACK之前也会被回调再次擦掉。

Core新增显式可选error_recovery_frames出口，现阶段仅这三个重置操作声明。失败事务回滚、原生错误ACK准备后，再读取当前权威状态，追加45201→45001→45101。没有重新执行重置，没有复用提交前的旧快照；其他操作没有该钩子，行为保持。状态组包先整组校验，不能返回半组恢复帧。

该恢复也覆盖SQL写入错误、必要ACK为空或异常、COMMIT被拒。若数据库读取或恢复编码持续不可用，仍保留非零ACK并记录恢复失败，不伪造空状态；客户端完整恢复需要故障解除后的正常读取/重登。没有自动无限重试。
