# GH-9 / A137-A138：成就领奖去重与状态守卫

来源：[发布仓库Issue #9](https://github.com/Mint-ARK/Alpha-Persei-Cluster/issues/9)，以及原报告health_audit_20261008_round93_achievement_claim.md。Issue还包含A52体力时间回拨、A152插画空选择，本票只处理用户指定的成就领奖部分。

Issue的A137不需要篡改库：同一个53004传入三份10101，原服务对每份累加奖励，但最终仅将同一行complete_flag置1。已有标记能挡后续请求，不能挡同包重复项。正常Lua会过滤重复列表，因此原报告未将其认定为普通点击自然复现。

本次处理放在成就领域服务，不在通用网关猜测业务状态：

- 输入ID按顺序去重，一份成就只累计一份配置奖励。
- 既有complete_flag继续表示已领奖，达标进度与已领奖分别校验。已领取返回原生2013「奖励已经领取过了」，未达成或缺进度行返回2005「未达到条件」，空/未知ID返回2。
- 批量请求全部资格通过后才标记、发奖。A138原先部分跳过却返回成功，客户端成功回调又将请求中全部ID设已领，因此不能继续部分成功。
- SQL条件更新只允许0→1且当前进度达标，实际更新行数必须等于去重后的请求数，再交InventoryService发奖。
- 直接调用服务也有保存点事务；失败恢复上下文通知。53004启用事务内准备17023差量与53005确认，必要编码失败回滚，后续可重试。
- 操作使用本次请求数据库创建服务实例，避免领奖中途由其他存档调用改写单例db绑定。未新增另一份独立领奖台账或防篡改机制，数据库仍为唯一持久权威。
