# A71：芯片拥有数量成就与重复广播

依据health_audit_20260922_round47_chip_closeout.md、A67实测服务回包、当前ChipService/事件总线/AchievementService与AchievementAction/AchievementData消费代码。

## 修复

- 条件260只统计已解锁且cat=kernel/type1的管理喵；261统计已解锁的secondary/type2、hero/type3、reviser/type4芯片。未解锁、NULL标记、未知类别或缺失/不匹配类型不算拥有；依据现有静态配置字段与客户端各解锁列表，不通过ID范围计算数量。
- 新增只处理7项芯片数量成就的小范围对账：一条聚合SQL读取资产数量，按当前配置门槛更新未领奖行。允许纠正这两种快照型条件的虚高进度及完成时间，其他累计型成就继续保持原单调规则；已领奖行的进度/标志/时间和既发资产保留。
- 解锁与装卸消费者不再delta累加；直接按同一资产快照对齐。装卸不新增拥有数，已对齐时不发成就包。generic trigger_condition的260/261入口也不能用delta或set_value伪造拥有数。登录、完整对账和领奖前共用这份规则，旧max不能再保住未领奖虚高。
- 角色AI/助战重复已解锁请求直接幂等返回，不改时间、不再发布首次获得事件；管理喵和次级芯片补齐首次解锁CHIP_UNLOCK，助战CHAR_CHIP_ACTIVATE接入数量对账。真实已配置资产可正常推进两类成就。
- 领奖前先按资产对齐，再执行原整单资格、0→1标记与真实Inventory发奖；保存progress再高也不能绕过拥有数量。失败整笔回滚，所以一次被拒绝的领奖不承诺持久保存对账结果；登录或合法事件仍会保存修正。
- 芯片小范围对账有保存点与通知检查点；SQL/差量编码失败不留下半份对账。50003必要回执准备也纳入Core事务，回执失败可回滚解锁、成就状态及本次待发通知。

未完成A68助战前置、A69解锁配置/条件及历史异常资产清理，不以本轮重复请求保护代替这些资格规则。

## 差量与Lua顺序

只在7项中实际进度或完成时间变化时发53003，不新增50001/53001/17009全量刷新。解锁先发真实成就差量，再50003；原生回调负责芯片解锁列表，不再重复服务端整列表推送。

AchievementRewardOp原来没有取走对账生成的pending成就包。本轮在17023资产差量之后、53005成功回执之前下发真实pending帧，顺序为[17023,53003,53005]。原生53005成功回调会标记已领奖，因此不能在回执后再用较早complete_flag=0的53003覆盖它。既有领奖回滚检查继续适用。

Lua53003按绝对进度更新process/rewardState，能够消费本次差量；但旧在线会话已加入的ready/canReceive列表缺少通用回退清理分支。此次部署需重登清空这类旧缓存，服务端守卫始终拒绝虚高领奖；不造假完成帧清理缓存，不声称服务端能修改客户端所有旧内存列表。

事件不再为每次解锁跑全领域reconcile，只查当前UID的chip与7项成就；重复已对齐事件无写入/通知。其他全领域登录对账保持原触发方式，未另做网络性能跑分。
