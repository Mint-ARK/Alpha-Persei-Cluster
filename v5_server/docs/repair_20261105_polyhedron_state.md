## 原生依据与数值边界

`polyhedronaction.lua` 的 18012/18014/18020 回调立即读取新状态或启动场景；当前 `polyhedrondata.lua` 调用 `UpdateProcess`，而模板实际方法是 `UpdatePocess`。因此在线使用完整 18001 作为可靠状态源，不依赖这条存在拼写差异的 18003 消费路径。

`polyhedronlobbyview.lua` 的继续探索直接 `LaunchPolyhedronBattle`，所以奖励/选门阶段的 54030 必须支持冷恢复，不能简单拒绝全部非战斗阶段。`battlepolyhedronstagetemplate.lua` 通过 `PolyhedronHeroCfg.standard_id` 加载系统角色；`battlecontroller.lua:SetPolyhedronHeroData` 直接使用局内 `health/max_health`。UDP 字段 10 已由当前 `battle_server.parse_battle_characters` 提供逐角色血量；完整且名单匹配的实报会保存，包括 0 HP。缺旧字段保留现值，非空错误名单/畸形字段拒绝结算。已删除按战斗时长和队伍位置虚构伤害、承伤、治疗量的旧代码。

`polyhedronterminalview.lua` 明确显示剩余重置次数，并使用 `WEEK_RESET_TIME`；`polyhedrondata.lua:GetBeaconMaxBeaconSelect` 明确引用 3001、3005、3011。静态合同通过只读导出器从 x64 原生配置提取，记录每个源文件 SHA256；新增神格、连携及信标条件合同，没有改客户端文件。

刷新仍为固定周一 05:00、7 天。45 历程经验和每周领史清零；46 终端经验、已点亮终端、解锁角色/信标和通关难度保留。终端剩余重置次数按上述原生周次数恢复 1；切版本和时钟回退不重开本周资格。

`ops_common.polyhedron_progress_v1/lifetime` 保存本轮开始后的实际战斗奖励币、放弃奖励币、击杀数、商店购买、升级门、结算积分、不同通关队长及有完整最终 HP 实报的健康通关。旧已解锁信标保留；没有凭余额/当前库存伪造历史累计。初始携带币不猜成历史奖励，旧累计不足的条件可能需要重新累积。原生信标 UI 的条件提示和红点仍需实机核对。

## 旧档与保留项

旧版已经处于 state=3、却没有新结算版本或回执的存档，无法证明过去资产未发。本轮将其视为已处理，不补发；历史金额无法重建时 18005 显示 0。不会倒扣现有资产。旧 state=2 对局在下一次合法修改时建立结算版本，之后能够正常产生新回执。旧档缺少明确最终通关标记时不追认难度通关。

以下仍是边界，不能据本轮通过而宣称完整玩法正确：

- 初始固定 10000 HP、原有奖励/积分/经验公式、按已进入层计算部分进度、随机货架与部分事件分布仍沿原实现。立即开局再放弃仍按现有公式结算，本轮仅堵无局/重复结算，不擅改奖励政策。
- 原有终端/信标属性和珍宝效果覆盖并不完整，基础复活次数与客户端上限也尚未校准。本轮校验资格与生命周期，不宣称全部终端/珍宝效果生效。
- 缺少逐角色 HP 字段的旧报告仍无法证明战后血量；没有伪造分摊或无证据回血。UDP 字段来自当前解析实现，尚无本轮客户端实战报文验收。
- 招募试炼类型 1 尚未实现；当前候选生成只提供付费/免费类型。无请求 nonce 的同类操作不能区分“前一节点迟到请求”与“下一节点相同选择”，不宣称跨新节点通用幂等。
- 已转移节点或新尝试后旧 54032 返回失效；没有保证所有 ACK 丢失后的旧请求都继续成功。
- 原生 54003 的当前通用 codec 将嵌套 `player_info` 误套皮肤结构；本轮测试按 p54 原始字段逐层核对系统模板 ID 和 hero_type，没有扩大修改通用 schema。
